# Watermelon Vector Converter UI/UX Audit

**Audited revision:** `5f71d4052d4c0436ffe743964ccbc815bb569480`
**Scope:** Android Compose application and Rust/Iced desktop application.
**Method:** Source-level interaction review, design-token inspection, shared-artwork inspection, and WCAG contrast calculation. This is not a substitute for moderated usability testing or a TalkBack/VoiceOver device pass.

> **Executive assessment:** The Android product has a coherent conversion concept and a promising visual system, but its primary flow needs stronger state handling, a more accessible color system, and lower cognitive load in file management. The desktop application is currently not usable as a converter from its standard launch path: after the branded splash it displays a placeholder rather than conversion controls. That is the most urgent issue in the entire product.

## Interaction design assessment

The Android home screen clearly presents two conversion directions and single-versus-batch choices, which is a strong start.[3] However, the primary action does not make the next step explicit: users are sent to a screen titled “Preview” before conversion has finished, where state visibility then breaks down. The core journey should read as one narrative: **Choose file → Validate → Convert → Compare → Export**. Each stage needs its own state and a clear escape hatch.

The Files experience is functionally ambitious, but its current mental model is unstable. “Marked” means queued for conversion, while “selected” means multi-file operations; both use secondary visual states and can co-exist with preview. Simplifying to one explicit batch-selection mode would improve learnability. A fixed bottom action bar should expose only the two to four valid next actions, and destructive operations should remain behind an overflow action and confirmation.

Batch processing has useful file-level and total progress indicators, plus cancellation and retry.[14] It needs richer trust cues: the archive name, estimated queue size before starting, current success/failure counts while running, and a completion report that offers **Export ZIP**, **View failures**, and **Start another batch** rather than a generic dismissal.

The desktop information architecture must be rebuilt around the converter rather than the splash. The existing separate viewer is a reasonable file-preview capability, but it cannot substitute for an input-to-output conversion workspace.[1] A practical desktop default screen should have a drop zone and “Choose file” button, a clear direction selector, source/output panes, an inline conversion status, and an export/copy action that appears only after a validated result.

## Accessibility and visual-system review

The contrast check is the most concrete accessibility concern. `FreshTeal` is used for small labels, navigation state, and action text despite failing the 4.5:1 normal-text threshold against white and off-white surfaces. `WatermelonRed` has the same problem when used as white-label button background.[6] [7] The proposed darker variants preserve the brand family while satisfying the measurable threshold.

Text sizing also leans too small in high-importance locations: 11sp navigation labels, 11sp card subtitles, 12sp operational metadata, and 12–13sp actions in previews.[3] [5] [8] These sizes should be reviewed under increased font scale and narrow device widths. All explanatory and operational copy should use Material typography tokens rather than scattered explicit sizes so scaling remains coherent.

Dark mode is only partially tokenized. Theme support exists, but multiple screens bypass semantic color roles with direct white, light gray, or deep navy values.[6] [8] [10] This increases the likelihood of contrast regressions. A small semantic token layer—`contentPrimary`, `contentSecondary`, `surfaceMuted`, `divider`, `actionPrimary`, `actionDestructive`, and `canvasPreview`—would make the codebase easier to maintain and improve visual consistency.

## Priority refinement plan

| Horizon | Workstream | Refinement | Completion criterion |
| --- | --- | --- | --- |
| **P0 — block release** | Desktop core journey | Replace the desktop post-splash placeholder with a functional converter workspace. | A user can choose or drop SVG/XML, convert in either direction, see a result/error, and export or copy output without command-line arguments. |
| **P0 — block release** | Android state design | Render `Working` and `Error` states in the destination journey; do not show “Nothing to preview yet” after an initiated action. | Slow, failed, cancelled, and successful conversions are visually and verbally distinct, with recovery controls. |
| **P0 — accessibility** | Color system | Introduce accessible action colors and remove hard-coded light-mode values from dark-capable screens. | Normal-size button and navigation text meets at least 4.5:1 on its rendered surface; light/dark visual checks pass. |
| **P1 — core usability** | File management | Consolidate marked/selected behavior into a single batch mode; move secondary actions to contextual UI. | A first-time user can identify how to select, convert, move, and delete files without interpreting two selection concepts. |
| **P1 — conversion confidence** | Results and exports | Build visible validation/progress, comparison affordances, a readable code viewer, and explicit export confirmation. | Users can tell what was converted, whether visual parity is approximate, what was saved, and where it was saved. |
| **P1 — startup** | Launch experience | Replace the forced fake-progress animation with real initialization feedback and a short maximum presentation. | Warm starts are immediate; cold starts never show a misleading percent. |
| **P2 — permissions** | File access | Adopt progressive, task-based permission requests and clarify the all-files-browser trade-off. | Single-file conversion works with no broad storage permission; broad browsing is opt-in and explained. |
| **P2 — polish** | Components and branding | Replace text/emoji controls with semantic icons, export transparent/light-dark logo variants, and unify component spacing. | Navigation, actions, and brand assets look native, legible, and consistent across themes and platforms. |

## Recommended target journey

A refined primary flow should open on a task-first screen, not a loading treatment. The user chooses **SVG → VectorDrawable** or **VectorDrawable → SVG**, drops or selects a file, sees a compact validation summary, then starts conversion. During processing, show the source file name, progress state, cancel control, and a truthful message. On completion, present side-by-side previews, a compatibility notice where necessary, and one obvious primary action: **Export**. Copy, Share, source code, and technical properties remain available as secondary actions.

For batch work, the app should begin with a concise explanation of supported archive contents and expected output. After selection, show the number of eligible files before conversion. During conversion, expose successful/failed totals and the current filename. The completion screen should prioritize export, then failure review, then a new batch.

## Validation plan

Before implementing the visual polish work, verify the P0 changes through five scenario tests: a successful single forward conversion, a successful reverse conversion, a malformed-input failure, a slow conversion, and a cancelled batch. Test each at 100%, 130%, and 200% font scale, in light and dark modes, with TalkBack enabled. Then run a short five-person task test focused on choosing the correct conversion direction, understanding error recovery, locating exports, and performing a multi-file conversion.
